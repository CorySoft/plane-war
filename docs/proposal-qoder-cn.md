## 0. 主推

**P2 擦弹 / 危险度风险倍率**（B2 + B3 合并），次推 **P3 技能协同命名 + 双封顶**。

一句话理由：**这是目录里唯一一条"我们已经在计算、却把它扔掉"的玩法** —— `js/game.js:656-673` 每帧对每颗敌弹都已算出 `dist = hypot(player.x, player.y, b.x, b.y)`，算完只为比较 `dist < PLAYER.hitRadius` 一次，随后**数值即被丢弃**；P2 的边际成本因此接近零，而它补的是本项目唯一空白的能力轴（"这一秒怎么走"），且天然不碰 `SCORE_AXIS`。
为什么是现在：v0.5.2 刚把计时时长收敛成 `POWERUP_DURATION` 单源表、v0.5.3 刚立住灰度范式，**加一条"新轴 + 新单源表 + 新守护用例"的成本处在历史最低**；而 P2 的 A 级出处（Touhou graze 定义、Shikigami 距离倍率）是本次核验里少数被我逐字确认无需改口径的项。

组合 P3 的理由不是"顺手"，而是**两轴代码互不相交**：P2 只碰敌弹→玩家判定环、`js/hud.js`、`js/config.js` 新表；P3 只碰发弹期行为集（`js/bullet.js:114-154`）、命中结算（`js/game.js:660-730`）与图鉴文案。二者可同批不冲突、可分别回滚。

## 1. 六项评审口径逐条回答

### ① 复用哪些现有系统（含本次复核锚点）

| 玩家判定半径 | `js/config.js:420` `hitRadius: 20`（注释原文即"便于弹幕贴身擦过"） | 设计意图早已写在注释里；新增 `grazeRadius` 与它同表同处 |

| 子弹对象池 | 池 `js/bullet.js:11,21,65`；逐发字段重置块 `:57-63`、`:175-178`、`:259-262` | **必须在此三处清 `_grazed`**，否则池复用会让复用弹永不擦弹（见 §3 风险 2） |

### ② 是否碰 `js/ui/**`、是否新增 STATE/面板

**首版不碰。** 全部落在 `js/game.js`（判定环 + 计数器）、`js/config.js`（`DANGER` 表 + `PLAYER.grazeRadius`）、`js/hud.js`（危险度槽）、`js/meta.js`（成就字段）、`js/bullet.js`（池字段清理）。
**零新增 STATE**：不需要暂停、不需要输入分派，因此不触发 `STATE` 八态与输入路由，也就避开了"新面板吞点击"这一族缺陷（P1 级教训：首局帮助面板吞点击）。
**留二期的才碰 UI**：结算页新增"危险得分"行（`js/ui/overlays.js`）、图鉴擦弹条目页、帮助文案。

### ③ 是否新增乘算口子、如何过密度闸门

**不发分数、不发经验、不发明子弹** —— 这条是刻意的刹车设计：

- 难度轴唯一输入是 `score`（`js/game.js:454-455` `levelFromScore(activeScoreAxis, score)`）。**擦弹收益若走分数，就是 Garegga 反面教材的复刻**（涨分即涨难度 → 高手被自己的技术惩罚）。所以首版收益通道 = **护盾**（防守、有 `maxShield` 硬顶、不产出任何分数）。
- 危险度倍率首版**只作用于"危险度本身的显示与满槽判定"**，不乘任何伤害/得分；倍率的真实发放留二期，且届时必须写死上限并入 `DANGER` 表 + 守护用例。
- 密度闸门：P2 不新增弹，反而**降低"贴脸的隐性收益"**（把冒险显式化为资源）。但要注意副作用——它会**奖励玩家主动留在弹群里**，从而拉高同屏敌弹在玩家附近的驻留时间。约束：不改 `setHostileBulletBudget` 的额度（默认 140/140、战役按关卡、Boss Rush 120/90），只在集成用例里断言"P2 开启后同屏敌弹峰值不高于关闭时"。

### ④ 默认路径逐位一致的验证方式

- **开关**：`?graze=1` 灰度（与 `?campaign=` / `?bossrush=1` 互斥语义沿用现状：战役优先）。
- **主证据**：固定 LCG 随机源 + 固定 `performance.now` 步长，HEAD 与工作树各跑 **800 帧 / 2400 帧**，快照对比（状态/分数/等级/玩家/敌机/子弹/特效计数）。**不带参数时新增分支必须在 `hypot` 之后**（`else if`），不改变任何既有比较的顺序与短路，理论上快照恒等，用实测兜底。
- **反证式用例（我更看重这条）**：故意把 `DANGER.grazeRadius` 设成 `hitRadius` 同值，用例应**立刻变红**——证明"擦弹环确实被走到、且断言真的在测它"，避免重演"smoke 报 OK 却从未进对局"那类空证。
- 补 3 条单元测试：① 每颗敌弹只计一次（同弹二次进入环不叠加）；② **池复用后 `_grazed` 被清零**（复用弹仍能被记录）；③ 无敌期不计擦弹（见下条刻意取舍）。
- smoke 四路径 + bench 六项等价沿用；新增模块（若有）必须同步 `deploy-versioning` 产物计数（30→31 的先例已在 inventory 记为坑）。

### ⑤ 成本 S/M/L 与首版可交付边界

**P2 = S（我的估法偏保守，取 S~M 下沿）**；**P3 = S**。

首版（可上线、玩家可感知、零 UI）：
1. `PLAYER.grazeRadius` + `DANGER` 表（起值 `grazeRadius: 34`、`decay`、`capPerRun`、`full`）；
2. 敌弹擦弹判定环（`else if`，每弹一次）；
3. HUD 危险度槽 + 危险计数；
4. **满槽 → 1 层护盾**，受 `maxShield` 与 `DANGER.capPerRun`（建议 3）双重硬顶；
5. 成就 1~2 条（本局擦弹 N 次 / 满槽 K 次）+ 本地纪录 `bestDanger`；
6. 灰度参数 + 上述测试缝。

明确留二期：擦弹得分轨（要先决定 `best`/星尘是否含它，属语义裁定不能顺手改）、倍率真实作用于奖励、结算页新行（碰 `overlays.js`）、图鉴擦弹条目、擦弹音效与"擦过"粒子、慢速移位 `B1`（focus 模式——它才让擦弹变成**主动技巧**，但需要改移动手感，风险另议）。

### ⑥ 是否依赖被阻塞项

**不依赖 P-D（随机源收敛）**。P2 是判定与记账，不需要可复现随机；只有每日挑战（A13/C13）与回放（E3）被 P-D 硬阻塞。次推 P3 也不依赖（协同乘算读现有状态，无新随机源）。

## 2. 刹车设计（对应目录 §1.4 Garegga 反面教材）

| 风险 | 刹车 |

## 3. 风险与反证（可证伪）

**风险 1（我认为最可能致命）：本项目玩家根本不会主动擦弹。**
这是一款**自动射击 + 竖屏触控**的游戏——手指遮挡下半屏、44px 触控热区、无低速模式（`B1` 未做）。街机的擦弹建立在"精确走位 + 判定点可见"之上，我们两条都没有。若擦弹只是**被动发生的噪声**，满槽护盾就变成"活久见奖励"，玩法不成立。
**可证伪验证**：上线前用固定 LCG + 现有 smoke 键盘模拟跑 20 局，统计每局擦弹事件数与满槽次数；再用手动走位 5 分钟实测一组。**判据：若模拟对局每局擦弹 < 20 次或满槽 < 1 次，则撤销"满槽→护盾"的主动收益，改为纯计数 + 结算展示**（即把 P2 降级为度量项），并优先做 `B1` 低速移位再回来谈收益。这条判据是预先写死的，不许事后调。

**风险 2（工程性，我踩过同类）：对象池残留。**
`_grazed` 若不在 `js/bullet.js:57-63`、`:175-178`、`:259-262` 三个重置块里清零，被复用的敌弹会**永远不再计擦弹**，且**不报任何错**——表现是"危险度槽后期几乎不动"。这与 v0.5.1 修掉的 `_deathExplosion` 陈旧参数、以及 `uid` 池复用是同一族缺陷。§1-④ 的用例②专门锁它。

**风险 3（体验性）：判定环过宽会让"没中弹"变得不可信。**
`hitRadius` 20 → `grazeRadius` 34 是 1.7 倍；若美术判定点不明显，玩家会认为"明明穿过了却没算"或"算得太松"。首版需在 HUD 显示判定点（`B1` 的一部分代价），或把 `grazeRadius` 收到 30 并用实测调。

**刻意取舍（必须写进文档以免被当成 bug）**：现有循环在 `js/game.js:661` 有 `if (player.invincible > 0) continue;`，位于 `hypot` **之前**，因此**无敌期不计擦弹**。街机通常允许无敌期擦弹，但把 `continue` 后移会改动默认路径的控制流顺序；为守住"默认零变化"，首版接受"无敌期不擦弹"，二期若要让无敌期也计，须单独立项并用快照取证。

## 4. 对其它候选的排序意见（最不认同 2 项）

**① P5 突变词条 / 每日 BUFF 池 —— 现阶段最不该做。**
- 它的**出处已被我核验撤回**：`research-mobile-shmup.md:85` 所引原文没有"每日 1 正 + 1 反词条"，实际是"三选一随机 BUFF（局内）"，与我们**已有的升级三选一同构**。也就是说 P5 目前是**零先例的自研设计**，却挂着"成熟产品验证"的名。
- 更要命的是接入面：突变要改的是**读取散点**（生成率、道具早/晚权重、敌机速度与血量、玩家承伤），而"数字散在多处、改一漏二"正是本项目过去两个版本才还清的债。它需要一层 override 表 + 逐点接线 + **全量数值重新验证**，成本 M、回归面却接近全系统。我们没有任何遥测能告诉我们"词条手感不对"，这类改动在本项目里是**盲改**。
- 结论：留到 P-D 之后，且必须先把所有被突变触碰的常量收敛成单源表（像 `POWERUP_DURATION` 那样），否则等于给"改一漏二"开新入口。

**② P8 装备三维树 / 装甲行为（C9+C10）—— 第四套平行养成，方向性风险。**
- 本项目**已经**有四条进度通道：28 技能（局内）、12 天赋、9 条商城线、机型解锁。P8 会再加一条"装甲 × 副武器 × 僚机"三维树，它服务的动机（长线刷取）与 E5/E6 重叠，却带来**新的乘算入口**——尤其"击中概率升武器等级"这类装甲行为，等于绕开 `SKILLS.max` 上限从后门加等级，直接冲撞软上限纪律。
- 来源等级只有 B（雷霆战机，且其数值体系绑着体力/内购，我们已排除 E7/E8/F1）。**一个依赖付费墙才成立的系统，砍掉付费后剩下的只是复杂度。**
- 若真要长线深度，我会选 E6「跨局解锁目标（解锁**新选择**而非叠伤害）」+ P3（命名协同），两者都不新开乘算口子。

顺带对**被主持人排序靠前但我有不同意见**的一条：P1（Boss Rush 升格）我**不反对方向，反对顺序**。它必然碰 `js/ui/**`（菜单入口 + `STATE` 分派），而"无通关条件的无限车轮"即使升格也只是把灰度参数换成菜单按钮，玩家现在已能通过 `?bossrush=1` 玩到——**同一批预算花在 P2 上会多出一条全新能力轴，花在 P1 上买到的是一个入口**。P1 应当和"N 轮通关条件 + 轮次 HUD"打包，才有可交付的完整感。
