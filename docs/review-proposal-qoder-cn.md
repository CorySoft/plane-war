## 2. 分歧裁定：v1 回报走「星尘兑换」还是「局内护盾」

### 2.1 星尘是否违反「擦弹分不进 score」的刹车？——不违反，但也**不是物理隔离**

- 直接路径干净：难度只读 `score`（`js/game.js:454-456`），没有任何一处难度输入读 `stardust`。
- 但存在一条**滞后一局**的闭环，且今天就是活的：
  `星尘 → 商城「得分加成」`（`js/config.js:247`，+5%/级，max 5）`→ 得分速率`（`js/game.js:1105 v *= (1 + shopFxCache.scoreBonus)`）`→ score → levelFromScore/rankFromScore → 难度`。
- 所以 §6 把它写成「物理隔离」**越界**：准确说法是「与既有收益通道共用同一条滞后回路，不新增风险等级」。这条批评同样适用于现有 `earnStardust(score)`，不是他的新发明——但方案文档必须如实标注，否则二期有人拿「物理隔离」当免检依据。

### 2.2 星尘通道真正的三处失守（按致命度）

**(a) 「每局上限」这个口径在本仓不存在，不能复用。**
`bonusStardust`（`js/meta.js:264-271`）只有 `if (amount <= 0) return;` + `saveNow()`，**无上限、无按局概念**。全仓两条「额外星尘」通道各自的限额口径都不是「局」：

| 通道 | 锚点 | 实际限额口径 |
|---|---|---|
| 每日任务 | `js/meta.js:488-497 claimQuest` | 每日、每条一次性（靠 `q.claimed`） |
| 成就 | `js/meta.js:513-521` | 永久一次性 |

⇒ 「每局 +20」将是**第一条按局发币**的通道，且对一日多局毫无约束。量级对照：`DAILY_QUESTS` 全部 5 条 = 5+5+3+4+3 = **20 星尘/天**（`js/config.js:476-480`），而其中 `q_runs` 的目标定义就是「今日完成 3 局」（`js/config.js:478`）→ 玩家打满 3 局即 +60/天，**单日新增 = 既有每日任务总预算的 3 倍**。（回答主持人问题：`meta.js:266` 附近有落盘基建可复用——`todayKey()` `js/config.js:484` + `q.claimed`——但那是**每日**口径，不是每局。）

**(b) 平顶 +20 与既有 400:1 曲线不同构，实测直接打脸他自己写的验收门槛（§5.4「增幅 < 15%」）。**
基础产出 = `floor(score / META.stardustPerScore)`，`stardustPerScore = 400`（`js/config.js:428`，注释自陈「一局 2 万分 ≈ 50 星尘」）：

| 本局得分 | 基础星尘 | 叠加 +20 后增幅 |
|---|---|---|
| 3,000 | 7 | **+286%** |
| 5,000 | 12 | **+167%** |
| 10,000 | 25 | +80% |
| 20,000（基准局） | 50 | **+40%** |
| 60,000 | 150 | +13% |
| 150,000 | 375 | +5% |

而 +20 封顶极易触达：`grazeScore = Σ 10 × 倍率(1.0~1.6)`，约 30~40 次擦弹即满 400 → 兑换 20。**任何一局只要认真贴弹就吃满上限**，于是奖励变成「固定补贴」，且**逆进**——分局越弱、占比越高，恰好与「风险回报奖励技术」的意图相反。要落进他自己设的 <15%，上限必须 ≤7；或改成与既有曲线同构、随局长缩放的换算（`grazeScore / (stardustPerScore / k)`）。

**(c) 帧率敏感的原始计数被兑换成不可回滚的账号余额。**
进入兑换的唯一原始量是擦弹计数，而它由 14px 环带的抽样帧数决定（§3.2）。30fps 设备整段跨过环带 = 该弹永久不计 → 在「局内护盾」方案里这只损失一次局内机会、下一次满槽可补；在星尘方案里它直接折进 `localStorage` 的跨局余额，**误差不可回滚、也不可在测试里复现**（smoke 用固定 dt，真机不用）。

### 2.3 反向自检 + 裁定

护盾通道也要接受同一把尺：它是 EHP，确实提升玩家强度，但 ① 不写 `score`/`xp`/`stardust`（难度输入零变化，LCG 差分可验）；② 已被两处既有上限钳住（`js/config.js:51 maxShield: 3`；现成的一行范式 `js/game.js:1163 player.shield = Math.min(player.maxShield, player.shield + 1)`，对所有机型生效，基线即有 3 上限、`js/player.js:74 shield: 0` 起始）；③ `js/player.js:475-493` 已有护盾弧的 canvas 表现，零新美术。

**裁定**：两条通道都能过 Garegga 刹车，差别不在安全性而在**反馈位置**——护盾在同一秒可感知，星尘在本局结束之后才以数字出现。据此：

1. v1 采他的**账本 + HUD + 密度/隔离设计**，采我的**回报通道（局内护盾，`maxShield` + 每局次数双钳）**；
2. 星尘兑换**整体后移二期**，解锁须同时满足三条件：换算式与 `stardustPerScore` 同构；限额口径改为**每日**（复用 `todayKey` + `q.claimed`），量级 ≤ 每日任务一半（≤10/天）；`test/balance.test.mjs` 新增断言把这条通道计入——现有 5 处星尘护栏（`:113`/`:119`/`:129`/`:137`/`:163`）全部由 `stardustPerScore` 静态折算，**新通道对它们完全隐形**，这正是我们用 `POWERUP_DURATION` 守护表治过的「改一漏二」同型漏洞；
3. **v1 若坚持「零局内回报」，就必须同时删掉倍率**：×1.0→1.6 只放大一本不进 `score`、不进掉落、不进任何结算的账，把 1.6 改成 1.0 玩家体验零差别。空转乘数只增加测试面，不增加可感知差异——复杂度必须换来玩家能感觉到的东西。

## 3. 三条最需要改的点

### 3.1 【最高】换掉 v1 回报通道（星尘 → 局内护盾），星尘按 §2.3 三条件后移
理由与证据见 §2。一句话：**上限口径不存在 + 平顶补贴逆进 + 帧率误差落盘不可回滚**，三条里任何一条都足以让「+20/局」回到桌面。

### 3.2 【高】把环判定合并进现有循环的 `else if`，并解决 14px 环带的帧率坍缩
他的实现是「子弹更新后**另起一遍**扫描」（§3①/§5.3）。三处后果：

- 必须复刻 `js/game.js:658-661` 的四道过滤（`!b` / `friendly` / `!playerAlive` / `invincible > 0`），漏一道就是「自家弹计擦弹」或「无敌帧刷擦弹」；
- 「命中当帧不计擦弹」在他那里要靠**两遍循环谁先跑**来规定（顺序耦合），`else if` 由构造消除。顺带：这一句在 `js/game.js:663 dist < PLAYER.hitRadius` 的语义下不是伪命题而是**没有可执行判据**——命中弹当场被 `removeBullet` 回收，"当帧"无从观察。请改写为弹道级断言：*一颗直线穿心弹 → 擦弹 0 次、命中 1 次*；
- 成本上重复开方没必要：擦弹判定只需比较 `d²` 与 `34²`/`20²`。本机实测同结构比值（绝对值不可信，见附注）——单循环 `else if` : 双独立扫描 ≈ **1 : 1.98**；`Math.hypot` 版 : 平方距离版 ≈ **4.5 : 1**。所以性能**不是**风险（他的 `<0.05ms/帧` 大概率轻松通过），但实现方式应当是「复用 `:662` 已算好的那个 `dist`」。

**帧率坍缩（这是 §6「不依赖 P-D」结论的真实边界）**：环带宽 `34 - 20 = 14px`，`dx = b.vx * dt * 60` ⇒ 每帧步进 = 声明速度（px/帧）。敌弹速度经 `js/level/patterns.js:50-70 validateSpeed` 允许 0.1~20：

| 敌弹速度 | 带内帧数 @60fps | @30fps |
|---|---|---|
| 2 | 7.00 | 3.50 |
| 4 | 3.50 | 1.75 |
| 8 | 1.75 | **0.88（可整段跨过）** |
| 20 | 0.70（**已经会漏**） | 0.35 |

处置二选一，并写进验收：**①** 环带随 dt 放大 `grazeRadius = hitRadius + max(14, spd * dt * 60)`（缺点：慢设备判定更宽松，账本跨设备不可比）；**②（推荐）** 改为「每弹最近距离」记录（`b._minDist = min(...)`，出带时若 `≤ grazeRadius` 计 1 次）——与帧率无关，只多一个字段和一次比较。
新增验收条款：**同一走位脚本在 30fps 与 60fps 下擦弹计数偏差 ≤10%**。他 §5.1 的手机视口脚本是本轮最好的验收设计，建议直接升格为共同验收，并补这一条帧率维度。

### 3.3 【中】三个初值落表 + 上锁 + tripwire
现状实测：`grep -rni "graze|擦弹" js/ test/` = **0 命中**（改动未落盘，符合预期），但方案 §8 只承诺「+6~8 条用例」，**未点名锁哪三个数**——即 `+20/局`、`1.0→1.6×`、`34px` 今天没有任何守护测试（回答主持人第三问：**没有**）。更糟的是环的**内**边界同样是浮动的：`hitRadius: 20` 全仓仅 `js/config.js:420` 定义 + `js/game.js:663` 读取，无测试锁定，谁调它谁就静默改写擦弹带宽度。

要求补三件：
1. `js/config.js` 增加 `export const DANGER = Object.freeze({ grazeRadius: 34, mulStep: 0.05, mulMax: 1.6, decaySec: 2.5, perGrazeScore: 10, capPerRun: 3 })`，HUD 文案与结算兑换都从表里取；
2. 守护断言：表值 ↔ 实际行为一致（仿 `POWERUP_DURATION` ↔ 图鉴「N秒」那套既有写法）；
3. **tripwire**：把 `grazeRadius` 临时改成 `=== PLAYER.hitRadius`，必须至少有一条测试变红。否则该机制有一个零告警的退化方向（环带宽度 = 0 ⇒ 永远 0 次擦弹，全绿）。

## 附：测量条件（诚实标注）

本机 2 核 / load 0.53 / node v24.22.2 arm64。**绝对 ms/帧 不可用于验收**：对照组「280 元素数字数组单次遍历」测得 **370 ns/元素**（正常应 ~1 ns），而「1e6 次纯加法」= 4.3 ns/次 —— 属性访问在该环境被严重放大，疑似 cgroup/QEMU 侧开销。故本文件只引用**同结构重复测得的比值**（±3%，3 次重复）。`Math.hypot` 21.1 ns/次 vs `sqrt(dx²+dy²)` 4.0 ns/次 属可信的纯算术测量。真机门槛（§3.2 的 `<0.05ms/帧`）请在低端安卓上跑，本机数据只能用于比较实现方案的相对倍数。
