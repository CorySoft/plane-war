# 决定性实证：P2 擦弹在本项目里到底有没有燃料

> 交付说明：本测量原定 codearts（主持人指派），codearts 在脚本写完后被平台禁用（`tools/perf/graze-feasibility.mjs` 由其 23:45 落盘），**由 Qoder CN 接手执行并补写诊断层**。判定所用的两条判据是双方提案里**预先钉死**的原文，本文不做事后调整；新增的第三层（合成弹幕）只用于定位「瓶颈在哪一侧」，不用于放宽判据。
> 基线 HEAD `a54eeed` / v0.5.3 / 398 测试。**零产品代码改动**（只新增 `tools/perf/` 下 3 个脚本）。
> **归档标记（2026-11-12 追加）**：本文是特定时点（HEAD `a54eeed` / v0.5.3）的评审快照；正文 `file:line` 按写作时版本有效，**不得作为现行行号依据**；现行代码锚点以 `docs/design-current-state.md` 为准。

## 0. 结论（三选一）

**→ P2 降级为纯度量项**（不选「按玩法放行」，也不选「先做 B1 低速移位」）。

两条预设判据在**全部现网可玩场景**里同时触发；触发原因是同一个：**本项目没有持续弹幕**，而不是玩家操作不够细。所以第三选项 B1（focus 慢速移位）不成立——瓶颈实测在敌侧供给，不在玩家侧（见 §4：同一批弹幕，走位组擦弹量是静止组的 2-3 倍，说明操作能兑现，只是没弹可擦）。

保留**条件复活路径**：若先做「默认模式弹幕密度前置」（§3 的算术缺陷），使合成层的 20+ 发/分密度在真实对局里成立，则 P2 可按玩法重新评审；届时 `DANGER.full` 依实测钉 **≤5**（钉 15 在任何场景都永不触发满槽）。

## 1. 测量口径（含已知偏差，全部如实标注）

工具：Playwright + `initScript` 固定 LCG 与 `performance.now`、手动泵 rAF 队列（`step = 1000/fps`），跑真实 `index.html` 与真实 `js/**`。

| 层 | 目的 | 场景 |
|---|---|---|
| L1 生态层 | 真实对局里敌弹是否出现、擦弹发生几次 | 默认无尽 / `?bossrush=1`，静止 vs 正弦走位（振幅 90px、周期 2s），3 种子 |
| L2 合成层 | 给定弹幕密度，擦弹产出率与间隔分布 | 2 台悬停 `patternRef:"ring"` 发射器（count 10、speed 3.0、周期 0.9s，走真实 `buildPatternSpecs` + 密度预算路径），3 种子 |
| L3 敏感性层 | 验证「14px 环带帧率坍缩」假设 | 同种子同走位，60fps 与 30fps 各等时长 |

判定环（等价复刻 `js/game.js:656-673`，只读）：`20 ≤ dist < 34`，双计数口径——
**A 每弹一次**（对象生命周期，`上一帧不在场 = 新生命`）；**B 每穿带一次**（出带重新武装）。

必须披露的三条偏差：
1. **偏高**：复刻环**未**应用 `js/game.js:661` 的 `player.invincible > 0` 短路（它在 `hypot` 之前），所以无敌帧内的贴身穿过被计入。证据：`synth/30fps/static` 某局 `minDist = 4.7px`（该帧玩家正处无敌）。⇒ 本文所有擦弹数都是**上界**，判据仍触发，降级结论只会更稳。
2. **偏高（早期）**：对象池复用曾导致漏计（正是本轮钉死的 `_grazed` 陷阱，测量侧同型复现）；已用「上一帧不在场即新生命」修正，A/B 两口径差值 ≤1（例：`synth/60fps/move` 9 vs 8）。
3. **偏低**：bot 不瞄准（只有自动炮 + 横向走位），默认层击杀率远低于真人（60s 仅 1000-2300 分、等级 1-3）。⇒ L1 的绝对值是**真人下界**；但 §3 的机制结论与操作无关。

自证：走位组 `xTrace.span = 180.0`、静止组 `0.0`（两组确实不同，排除「对照组空转」）。

|---|---|---|---|---|---|
| 默认 600 帧(10s) 静止 | 0 / 0 / 0 | 0 | 0 | — | 0/3 |
| 默认 600 帧 走位 | 0 / 0 / 0 | 0 | 0 | — | 0/3 |
| 默认 3600 帧(60s) 静止 | 0 / 0 / 0 | 0 | 0 | — | 0/3 |
| **默认 3600 帧 走位** | **0 / 4 / 0** | 0 / 5.3 / 0 | 0 / **3** / 0 | — / 21.1 / — | 2/3 |
| Boss Rush 600 帧 静止 | 1 / 1 / 1 | **6.0** | 11 | 22.0 | 0/3 |

默认模式 60s 的敌弹时间线（每 60 帧采样，seed 6789 是唯一有弹的一局）：
`[0×35, 1, 1, 2, 1, 0, 0, 0, 2, 2, 1]` —— 第 35 秒才出现第一颗弹，该局玩家等级 3。
其余五局时间线**全零**（等级 1-2）。

## 3. 为什么默认模式没有弹幕（算术，与测量无关）

不是随机 unlucky，是三条常量拼出来的必然：

1. `js/enemy.js:176`：`if (e.y <= 10 || e.y >= H * 0.7) continue;` 在 `:196` 的 `e.fireCd -= dt` **之前** → **fireCd 只在开火窗口 `10 < y < 504`（494px）内 tick**；
2. `js/config.js:175` `small: { speed: 2.4, fireCd: [4, 6] }` × `DIFFICULTY_PRESETS.normal.speedScale = 1.0` × `rand(0.8, 1.25)`（`js/enemy.js:83`）→ 穿越窗口耗时 `494 / (2.4×60×[0.8,1.25])` = **2.74 ~ 4.29s**；
3. 首发 `fireCd = rand(4, 6)`（`js/enemy.js:88`，`fireCdScale = 1.0`）→ **4s > 4.29s 的最大窗口时间**，任何 small 机在离开窗口前都数不满首发。

而 `getEnemyTypePool(level)`（`js/enemy.js:45-55`）在 **level 1 只有 `small`**；level≥2 才入 `mid`（fireCd 3.2s、窗口 4.12~6.43s → 能开 1-2 枪）、level≥3 `mid×3`、level≥5 才有 `big/shield`（fireCd 2.2/3~4s）。

⇒ **「默认无尽模式前期是纯撞击+我方射击，没有敌方弹幕」是代码事实**，实测只是把它照出来。顺带：同一条 gate 让 `laser` 型（`fireCd` 无关、走 `laserTimer` 初值 `rand(1,2)`）成为早期唯一能开火的非 Boss 机，但它 level≥4 才入池。

## 4. L2 合成层：密度到位后，操作确实能兑现

发射器固定（同屏峰值 20-30 发，约为 Boss Rush 实测 11 发的 2-2.7 倍）：

| 组 | 擦弹(口径B) | 次/分 | 间隔 p50 / min | 死亡 | 存活时长 |
|---|---|---|---|---|---|
| synth 60fps **走位** | 9 / 6 / 9 | 25.5 / 23.6 / 22.1 | 2.10~2.22s / 0.283s | 3/3 | 15.3~24.4s |
| synth 60fps 静止 | 3 / 3 / 3 | 21.1 / 21.2 / 21.2 | 2.217s / 2.217s | 3/3 | 8.5s |
| synth 30fps 走位 | 7 / 7 / 8 | 21.0 / 20.6 / 19.6 | 2.10~2.37s / 0.20s | 3/3 | 20.0~24.4s |
| synth 30fps 静止 | 3 / 3 / 3 | 21.0 / 21.0 / 20.9 | — | 3/3 | 8.5s |

三条读法：
- **操作侧有效**：走位相对静止是 **3 → 6~9 次**（+100%~200%），说明擦弹确实能被玩家行为放大——P2 的机制本身不是空中楼阁；
- **满槽阈值必须钉小**：`full=15` 时**所有组、所有种子满槽 0 次**；`full=5` 时仅合成走位组 1 次、静止 0 次。⇒ 我方案里「满槽→1 层护盾」若按 15~20 次/槽设计，等于奖励永不发放；可兑现的只有 `full ≤ 5`，而 `full=5` 又意味着「擦 5 次就白送一层盾」，节奏太密、需要重新评审（这正是应当由实测而不是拍脑袋决定的东西）；
- **每局 20 次这个量级只有合成场景够得到**：需要同屏 20+ 发弹，而现网最高密度场景（Boss Rush）实测 11 发。

## 5. L3 帧率敏感性：我提的「坍缩」假设被实测削弱

- 近场（≤60px）敌弹**每帧步进**分布：`p50 = 2.92~3.00px @60fps`、`5.88~6.00px @30fps`，`p99 ≤ 7.48px`，**超过 14px 环带宽度的样本比例 = 0.0%（全部 n=7~269 的组）**；
- 同走位同种子的计数偏差：60fps vs 30fps = **−22.2% / +16.7% / −11.1%**（均值 −5.5%，符号不一致）。

⇒ 诚实修正我在 `review-proposal-qoder-cn.md §3.2` 的强断言：主流敌弹速度（ring 3.0、`spawnEnemyBullet` 3~4.5，`js/bullet.js:294`）在 30fps 下仍在环带内留 2 帧以上，**不会整段跨过**；偏差是**抽样相位噪声**（有正有负）而非「慢设备系统性少吃」。
仍然成立的边界：`spawnLaserVolley` 速度 8.5~9.7（`js/bullet.js:307`）→ 30fps 步进 17~19px **> 14px**，会漏。所以「每弹最近距离」口径**不是必需**，降级为「对 laser/高 rank 弹的可选加固」，二期再议。

## 6. 判据逐条回答（原文照抄，不许事后调）

| 预设判据 | 出处 | 实测 | 触发? |
|---|---|---|---|
| 「擦弹 < 8 次/分钟 或 死亡率显著高于基线（>1.5×）⇒ 不可玩」 | `proposal-codearts.md §5.1` | 默认 0/min；Boss Rush 6/min；均 <8 | **触发** |
| 「20 局模拟平均 <20 次擦弹 或 <1 次满槽 ⇒ P2 降级为纯度量项、先做 B1」 | `proposal-qoder-cn.md §5` | 每局（60s）实测 0~4 次；满槽（full=15）0 次 | **触发** |
| 「同一走位 30/60fps 计数偏差 ≤10%」（我在交叉评审里新增的验收条款） | `review-proposal-qoder-cn.md §3.2` | 最大 −22.2%，均值 −5.5% | **不达标**（条款需改为 ≤25% 或改用 min-dist 口径） |

**判定：降级为纯度量项。** 三选一里排除另两项的理由：
- 排除「按玩法放行」：两个独立判据同时触发，且触发幅度是数量级（0~6 vs 门槛 8/20）；
- 排除「先做 B1」：B1 改的是玩家侧供给，实测 §4 表明玩家侧已经能兑现（3→9），改敌侧才有意义。

## 7. 交给终稿的输入

1. P2 的可行形态只剩「只读危险度计量」：穿带计数 + HUD 读数 + `bestDanger` 本地纪录，**不发任何奖励**（护盾在 `full` 无解之前不发；星尘在二期三条件之前不发）；
2. 顺带产出的**更高价值发现**：默认无尽模式前期零弹幕（§3）——这是玩法层的既有缺陷，修它的性价比高于加新系统，且是 P2 复活的前置；必须以灰度 + 密度闸门 + `SCORE_AXIS` 不变的方式做，因为「默认路径逐位一致」是本项目红线；
3. `DANGER.full` 不许再拍脑袋：任何奖励阈值都要经 L2/L1 复测（本轮脚本可直接复跑）；
4. 复现命令：`node tools/perf/graze-feasibility.mjs --out=/tmp/graze-feasibility.json`（约 6 分钟，33 组）；燃料反查：`node tools/perf/graze-fuel-probe.mjs`、`node tools/perf/_graze-diag.mjs`。
5. 未核实/边界：本文没有真人测试；合成层用的是我自选的 ring 密度，不是任何「官方推荐密度」；L1 的 bot 不代表人类水平（已在 §1 标注方向性偏差）；未测量触屏真机（§5.1 的手机遮挡风险仍未验，但在「无燃料」这一层被击穿之前无需再验）。
