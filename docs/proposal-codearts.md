# codearts 方案：P2 擦弹/危险度风险倍率（灰度 `?graze=1`）

> 基线：HEAD `a54eeed` / v0.5.3 / 398 测试。材料：`docs/gameplay-catalog.md`、`docs/existing-systems-inventory.md`、`docs/research-factcheck.md`。
> 本文只写方案，不改 `js/**`、不联网、不 commit。
> **归档标记（2026-11-12 追加）**：本文是特定时点（HEAD `a54eeed` / v0.5.3）的评审快照；正文 `file:line` 按写作时版本有效，**不得作为现行行号依据**；现行代码锚点以 `docs/design-current-state.md` 为准。

## 1. 主推与一句话理由

**主推 P2（B2 擦弹 + B3 离弹距离倍率，合并为「危险度」）**，灰度入口 `?graze=1`。

**为什么是它、为什么现在**：它是十项候选里唯一同时满足「来源最可靠（A 级）、不碰 `js/ui/**`、不新增 STATE/面板、不新增弹幕、不新增乘算口子、默认路径可逐位验证」的玩法——用 S 级成本把已经存在的弹幕密度变成**操作层**的风险回报，补上当前 28 技能/15 道具解决不了的那一半（"这一秒怎么走"）。

## 2. 为什么不是 P1 / P5（独立判断）

- **P1（Boss Rush 升格）**：原型 `?bossrush=1` 已经可玩且已上线，升格的主要产出是「菜单入口 + 轮次 HUD + N 轮通关条件」。在"探索新玩法"的目标下，S~M 成本买到的增量最小，且**必然碰 `js/ui/menus.js`**。它是好的"正式化"工作，但不是好的"探索"答案。
- **P5（突变词条）**：出处已被 `research-factcheck` 撤回（须改称自研），且接入面最宽（出生率 / 权重 / 敌机参数 / 得分），M 成本被低估；全局规则天然与 Garegga 的"难度螺旋"同构，首版很难给出令人信服的刹车证明。

## 3. 六项评审口径

### ① 复用哪些现有系统（`文件:行号`）

| 复用点 | 锚点 | 用途 |
|---|---|---|
| 敌方子弹数组 | `js/bullet.js:8 export let bullets` | 逐帧只读扫描、按 `uid`/实例去重 |
| 玩家判定半径 | `js/config.js:420 hitRadius:20` | **不改命中判定**，只在其外建"擦弹环" |
| 主循环/更新 | `js/game.js:320 update` | 在子弹更新后调用一次（带参数才进） |
| 参数灰度范式 | `js/modes/bossrush.js:39` + `js/game.js:74-77` | 复刻「模块期解析一次 + 状态默认 null」 |
| 状态初始化 | `js/game.js:1298 resetGame` / `:1344` | 新状态在 resetGame 创建 |
| HUD | `js/hud.js:38 drawHUD`（分区见 `:46/:109/:149`） | 新增一行危险度读数；**`js/hud.js` 不属于 `js/ui/**`** |
| 结算奖励通道 | `js/game.js:1221 gameOver` + `js/meta.js:266 bonusStardust` | 只有开启时把擦弹分换星尘（带上限） |
| 调试观测口 | `js/game.js:2063 window.__game` | 暴露 `getGraze()` 供测试/探针 |

### ② 是否碰 `js/ui/**`、是否新增 STATE/面板

**不碰 `js/ui/**`；不新增 STATE；不新增面板。**
- HUD 指示走 `js/hud.js`（独立文件，`inventory §8` 已把它与 `js/ui/**` 分开）；
- 提示用既有 `toast`（`game.js` 写、`js/ui/overlays.js` 画，不改 UI 代码）；
- 结算展示**不做新页**：擦弹分只进 HUD 与本局结束后的星尘兑换（既有 `gameOver` → `bonusStardust` 路径，无 UI 改动）。

### ③ 是否新增乘算口子 / 如何过密度闸门

- **不新增弹幕**，`setHostileBulletBudget`（`js/bullet.js:213`，执行点 `:275`）无需改动；若未来把擦弹接入 Boss 弹幕密集模式，仍走既有预算（Boss Rush 已设 120/90，`js/modes/bossrush.js:30`）。
- **不新增乘算口子**：危险度倍率**只乘"擦弹分"**，不参与：`score`、`SCORE_AXIS`（`js/config.js:336`/`351`，唯一派生于 `js/game.js:454-456`）、`COMBO`（`js/config.js:412`）、伤害/EHP、掉落。即它是一本**只读账**，不反馈到难度。

### ④ 默认路径逐位一致的验证方式

1. **LCG 差分（已有工具链）**：固定 `Math.random` 为 LCG、固定 `performance.now` 步长，对 v0.5.3 基线与改动树各跑 800/2400 帧，比较快照（state/score/等级/玩家/敌机/子弹/特效计数）——`diffs: []` 且字节数相同才算通过。
2. **关闭态断言**：未带参数时 `window.__game.getGraze()` 必须返回 `{ enabled:false }`，且 `js/modes/graze.js` 的状态对象不被创建（同 Boss Rush 的 `bossRush === null` 纪律，`js/game.js:157`）。
3. **分支隔离**：`update` 中只在 `if (graze)` 分支内扫描敌弹，默认路径不执行任何新循环。

**首版可交付（v1）**：

**留二期**：默认开启（需单独裁定，因为它改变默认对局）；擦弹音效/粒子；危险度与连击/得分轴的任何关联（需重新过评审）；离线/回放统计。

### ⑥ 是否依赖被阻塞项

**不依赖 P-D（随机源收敛）**。纯确定性判定（距离 + 计时），无随机、无回放需求；LCG 差分只用于默认路径验证，不要求全局 seed。

## 4. 机制细节（首版规则与初值）

| 项 | 初值 | 说明 |
|---|---|---|
| 命中半径 | `PLAYER.hitRadius = 20`（不变） | 保持现有手感与所有平衡测试 |
| 擦弹环 | `20 < dist ≤ 34` | 进环但不进判定；**命中当帧不计擦弹** |
| 单弹计一次 | 每颗敌弹一个 `grazed` 标记（子弹池复用时清零） | 防止贴身反复刷分 |
| 危险度倍率 | 每次擦弹 `+0.05`，上限 `1.6×`；`2.5s` 无擦弹线性回落到 `1.0` | 鼓励持续贴弹，而非"贴一下就退" |
| 擦弹分 | `+10 × 当前倍率` | **不进入** `score` / `SCORE_AXIS` / `COMBO` |
| 局末兑换 | `bonusStardust(min(floor(grazeScore/20), 20))` | 上限 +20 星尘/局，避免经济膨胀 |
| HUD | 左下：`GRAZE 128 ×1.4`（无擦弹时隐藏） | 复用 `js/hud.js` 现有布局，不新增面板 |

## 5. 风险与反证（可证伪）

1. **触屏不可玩（最大风险）**：竖版手机上手指会遮挡机身，34px 擦弹环可能"看不见也贴不到"。
   - **证伪方法**：手机视口（390×844 触屏模拟）跑脚本化"贴弹走位"60s，统计擦弹次数/分钟与死亡率；若擦弹 `< 8 次/分钟` 或死亡率显著高于基线（>1.5×），判为不可玩 → 环半径降到 28 或改为"近弹计时"（近弹 0.3s 计 1 次）再验。
2. **判定重叠导致"中弹也算擦"**：命中当帧若先记擦弹，玩家会觉得机制骗人。
   - **证伪方法**：确定性弹幕用例——子弹直线穿过判定圈，断言第 N 帧"命中事件"与"擦弹事件"互斥且同弹不双计。
3. **性能**：140 发敌弹 × 每帧距离计算。
   - **证伪方法**：`bench` 式测量 `update` 帧耗时，开启前后差值必须 `< 0.05ms/帧`；超标则改为每 2 帧扫描或空间分桶。
4. **经济/难度隐性反馈**：星尘可换永久升级，长期看仍是"越强越易滚雪球"。
   - **证伪方法**：兑换上限 +20/局 + 既有 `earnStardust` 不变；跑 10 局模拟，比较总星尘产出增幅 `< 15%`，否则下调换算率。

## 6. 刹车设计（回应 Garegga 反面教材）

- `SCORE_AXIS` 的"涨分即涨难度"是既有同构风险（`docs/gameplay-catalog.md §1.4`）。本方案的刹车是**物理隔离**：
  1. 擦弹分不进 `score`，因此不触发 `levelFromScore`/`rankFromScore`（`js/game.js:454-456`）；
  2. 不触发 `COMBO`，不改变掉落率与敌机强度；
  3. 兑换星尘有**每局硬上限**，且星尘商店是"解锁/小幅强化"，不是无限乘算；
  4. 若未来有人提议"擦弹分计入总分"，必须重新走评审——本文把它列为**明确禁止**，并建议加守护测试（`getGraze().score` 不得出现在 `score` 差分中）。

## 7. 对 P1~P10 的排序意见

**我的排序（从适合到不适合）**：P2 > P3 > P9 > P6 > P4 > P7 > P10 > P8 > P5 > P1。

**最不认同的 2 项（供交叉评审）**：
1. **P1 Boss Rush 升格**：它把 S~M 成本花在"给已经能玩的东西加入口和通关条件"上；探索阶段该优先买"新体验"，而不是"新按钮"。且它必碰 `js/ui/**`（`js/ui/menus.js`），与"灰度不碰 UI"的当前纪律相反。建议放到"正式化批次"，而不是本轮玩法选型。
2. **P5 突变词条**：出处被撤回后它已经是纯自研；同时它要动的接入点最多（出生率/权重/敌机参数/得分），而这些点分散在多个模块，任一处理不好就会产生 Garegga 式难度螺旋。M 成本偏乐观，首版很难做"可证伪"的验收。

补充：P3（技能协同命名+双封顶）我排第二，因为代码里乘算已成立（`docs/gameplay-depth-proposal.md` 读码结论），成本极低；但"双封顶"必须给出具体上限并加守护测试，否则会把既有 combo 变弱或变强。P9 排第三，但要注意它要改图鉴文案（`js/ui/codex.js`）→ 会碰 UI。
